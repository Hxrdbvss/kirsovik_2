### 1. Что сравнивает тест

Тест задаёт известные условия, выполняет действие и сравнивает наблюдаемое поведение с ожидаемым. Без ожидаемого результата запуск программы ещё не проверяет правильность. Полезный тест обнаруживает конкретный класс ошибки, а сообщение о неудаче помогает найти причину.

Модульный тест проверяет ограниченную часть логики. Интеграционный проверяет взаимодействие компонентов, например HTTP-метода и временной базы. Проверка интерфейса рассматривает пользовательский путь. Эти уровни дополняют друг друга, потому что правильная отдельная функция ещё не гарантирует верное подключение к форме.

### 2. Разобранный пример порога

Для учебного правила «от 80 % тема освоена» проверим сам порог и соседние значения:

```python
import unittest

def is_passed(score):
    return score >= 80

class ThresholdTests(unittest.TestCase):
    def test_boundary(self):
        self.assertFalse(is_passed(79))
        self.assertTrue(is_passed(80))
        self.assertTrue(is_passed(81))

suite = unittest.defaultTestLoader.loadTestsFromTestCase(ThresholdTests)
result = unittest.TextTestRunner().run(suite)
assert result.wasSuccessful()
```

Если заменить `>=` на `>`, проверка результата 80 обнаружит ошибку. В пяти вопросах приложения реально достижимы проценты 0, 20, 40, 60, 80 и 100; значение 79 здесь используется для проверки числовой границы самой функции, а не как возможный итог такого теста.

### 3. Состояние и повторения

Для наград мало проверить одну успешную отправку. Нужно отправить тот же тест повторно: попытки должны сохраниться, а баллы за первое освоение — не начислиться снова. Это проверка поведения системы со состоянием.

Изолированная временная база позволяет воспроизводить сценарий и не менять результаты пользователей. Тесты не должны зависеть от того, какой студент первым открыл сайт сегодня. Для ошибки ввода проверяется не только код ответа, но и отсутствие нежелательной записи.

### 4. Регрессия и объём проверок

Регрессионная проверка подтверждает, что после изменения прежнее нужное поведение сохранилось. После расширения материалов важно проверить загрузку всех тем и отображение примеров. После изменения транзакции дополнительно важны повторные и параллельные запросы. Не каждый цвет кнопки требует отдельного автоматического теста.

Количество успешных тестов не доказывает отсутствие любых ошибок. Нужно понимать, какие требования и ситуации они покрывают, какие внешние сервисы действительно запускались и какие условия остались непроверенными.

### 5. Типичные ошибки

- Проверять только удобный успешный вход.
- Брать ожидаемый результат из той же функции, которую проверяют.
- Использовать рабочую базу для очищающего теста.
- Заявлять проверку всей системы по результату одного модуля.

### 6. Что запомнить

Задайте входы, состояние, действие и ожидаемый результат. Проверяйте границы и последствия ошибки. Выбирайте уровень проверки по тому, где может возникнуть нарушение, и сохраняйте сведения о фактически выполненных сценариях.
