### 1. От пожелания к требованию

Требование описывает ожидаемое поведение или ограничение системы. **Функциональное требование** отвечает на вопрос «что должна делать программа». Например: «Администратор может найти студента по части имени». Требования к скорости, доступности или другим характеристикам уточняют, насколько хорошо и в каких условиях функция должна работать.

Фраза «сделать удобно» не задаёт наблюдаемый результат. Для проверки полезны конкретный пользователь, действие, входные данные и ожидаемое состояние. Требование не обязано диктовать строку кода или цвет кнопки, если это не часть задачи пользователя.

### 2. Разобранный пример критерия приёмки

Исходное пожелание: «Нужна админка со студентами».

Проверяемая формулировка: «После успешного административного входа поиск по тексту “Белов” показывает зарегистрированных студентов, у которых эта последовательность встречается в имени или идентификаторе, без учёта регистра».

Критерии проверки:

1. До входа список недоступен.
2. В исходном наборе выбранной группы поиск «БЕЛОВ» находит того же студента, что «Белов».
3. При отсутствии совпадений показано понятное сообщение.
4. Снятие фильтра снова показывает допустимые записи.

Такой набор позволяет отличить выполненную функцию от одной только нарисованной формы.

### 3. Контроль версий

Система контроля версий хранит историю выбранных изменений файлов. Коммит фиксирует согласованное состояние с сообщением о его смысле. Он помогает сравнить редакции и понять, почему изменилось поведение. Коммит не является автоматической резервной копией всего компьютера и не заменяет запуск проверок.

Обычная последовательность работы в отдельном учебном репозитории:

```text
git status
git diff
git add lesson.md
git commit -m "Expand Python lesson with worked example"
```

Команды приведены для изучения. Их выполнение в конкретном проекте требует существующего репозитория и настроенного автора. Добавлять в историю рабочие пароли, токены и пользовательскую базу не следует: история сохраняет и старые редакции.

### 4. Разделение ответственности

Интерфейс отвечает за показ и ввод, сервер — за правила, хранилище — за записи. Когда эти обязанности разделены, изменение оформления меньше затрагивает проверку ответов. Границу модуля выбирают по смыслу, а не ради максимального числа файлов.

Например, lesson.md содержит объяснение темы; функция проверки теста сравнивает ответы; компонент страницы показывает полученный процент. Изменение абзаца не должно незаметно менять начисление баллов.

### 5. Типичные ошибки

- Формулировать требование без проверяемого результата.
- Фиксировать в одном коммите несвязанные изменения без объяснения.
- Считать наличие истории доказательством работоспособности.
- Дублировать одно бизнес-правило в нескольких независимых местах.

### 6. Что запомнить

Требование должно позволять проверить результат. Контроль версий объясняет историю изменений, а модульная структура ограничивает область их воздействия. Перед реализацией полезно записать критерий приёмки, а перед фиксацией — посмотреть различия и результаты подходящих проверок.
